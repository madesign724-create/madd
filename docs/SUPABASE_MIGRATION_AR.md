# ربط بيانات MADD بـSupabase PostgreSQL

**الحالة:** مكتمل ومتحقق منه في بيئة التطوير.  
**المشروع المستهدف:** `ddfpymanvyvjjnqcvsuw`  
**نطاق هذا التغيير:** قاعدة البيانات العلائقية فقط؛ لم تتغير واجهات تطبيق MADD أو صلاحياته أو تدفق الصور.

## النتيجة التشغيلية

يستخدم خادم MADD الآن متغير `SUPABASE_DATABASE_URL` بوصفه اتصال قاعدة البيانات المفضل، مع إبقاء `DATABASE_URL` بديلاً احتياطياً لتسهيل العودة المؤقتة عند الطوارئ. جرى تحويل مخطط Drizzle وطبقة البيانات من MySQL إلى PostgreSQL، ثم إنشاء الجداول والفهارس المطلوبة على Supabase.

| البند | النتيجة |
|---|---|
| اتصال PostgreSQL بمشروع Supabase | ناجح |
| إنشاء جداول MADD | ناجح |
| نقل بيانات MySQL الحالية | ناجح وغير هدمي |
| اختبار إضافة قسم تشطيبات | ناجح ثم حُذفت بيانات الفحص |
| اختبار إضافة منتج وصورة له عبر طبقة MADD | ناجح ثم حُذفت بيانات الفحص |
| اختبار الانحدار الكامل | 34 اختباراً ناجحاً، واختبار واحد متجاوز |

## ماذا يحفظ Supabase؟

يحفظ Supabase الآن بيانات التطبيق المهيكلة: المستخدمين، الفريق، إعدادات الشركة، الخدمات، تقسيمات الكتالوج، المنتجات، روابط الصور، المشروعات، مراحلها، اختيارات العميل، المرفقات، وإشعارات الأجهزة وسجل النشاط الإداري. وبالتالي عند إنشاء قسم تشطيبات أو منتج من لوحة الإدارة، تُحفظ بياناته في قاعدة سحابية واحدة وتصبح متاحة لجميع مستخدمي التطبيق بحسب الصلاحيات.

> عند إضافة صورة، تُحفظ **بيانات الصورة ورابطها** في Supabase. أمّا الملف نفسه فيبقى في خدمة التخزين S3 المهيأة للتطبيق عبر `server/storage.ts`. هذا فصل مقصود بين قاعدة البيانات والملفات، ولا يمنع ظهور الصور أو حفظها مع الكتالوج.

## التحقق الذي تم تنفيذه

استُخدم اختباران لا يتركان بيانات تجريبية بعد اكتمالهما. يختبر الأول الاتصال المباشر بـPostgreSQL. ويُنشئ الثاني خدمة وقسم كتالوج ومنتجاً ورابط صورة باستخدام دوال MADD الإدارية الحقيقية، ثم يقرأ الصورة ويزيل كل بيانات الفحص. لذلك فهو يتحقق من المسار الذي تعتمد عليه لوحة الإدارة عند إضافة الأقسام والمنتجات والصور، وليس من وجود الجداول فقط.

| اسم الاختبار | ما يثبته |
|---|---|
| `supabase-connection.test.ts` | إمكان اتصال الخادم بقاعدة Supabase المستهدفة |
| `supabase-catalog-persistence.test.ts` | حفظ قسم ومنتج وصورة، وقراءتها عبر طبقة بيانات MADD، ثم تنظيف البيانات |

## تشغيل الترحيلات ونقل البيانات

ملف `drizzle/0010_supabase_postgres_baseline.sql` ينشئ مخطط PostgreSQL الأساسي بصورة غير هدمية. وتوجد أداة نقل في `scripts/migrate-mysql-to-supabase.mts`؛ تبدأ دائماً بمحاكاة قراءة فقط، ولا تحذف أي سجل من MySQL أو Supabase عند التطبيق. تستعمل الأداة `ON CONFLICT DO NOTHING` حتى لا تكرر الصفوف الموجودة.

```bash
# محاكاة فقط: يعرض عدد السجلات في قاعدة MySQL المصدر
pnpm tsx scripts/migrate-mysql-to-supabase.mts

# نقل محافظ على البيانات بعد مراجعة المحاكاة
pnpm tsx scripts/migrate-mysql-to-supabase.mts --apply
```

## التعليمات اليومية للمالك

لا يوجد إجراء إضافي مطلوب عند إضافة بيانات جديدة. يسجل مالك التشغيل الدخول إلى لوحة الإدارة، ويفتح تبويب **الكتالوج**، ثم ينشئ الخدمة أو التقسيمة أو المنتج ويرفع الصور. الحفظ يتم على Supabase تلقائياً عبر الخادم؛ كما يظهر الحدث في بطاقة آخر التعديلات وسجل النشاط الإداري.

## ضوابط قبل النشر العام

ينبغي حفظ `SUPABASE_DATABASE_URL` و`SUPABASE_PROJECT_ANON_KEY` في إعدادات الأسرار فقط، وعدم وضعهما في الشيفرة أو في رسائل المحادثة. كما يجب تفعيل النسخ الاحتياطي للمشروع من لوحة Supabase، وحفظ نسخة دورية من مخطط القاعدة قبل ترحيلات مستقبلية. عند تحديث التطبيق لاحقاً، يعاد تشغيل `pnpm check` و`pnpm test` ثم اختبار إضافة قسم وصورة من هاتفين مختلفين.

## الاستعادة عند الحاجة

إذا ظهرت مشكلة في اتصال Supabase، لا تحذف أي جدول. يمكن مؤقتاً إزالة `SUPABASE_DATABASE_URL` من أسرار بيئة التطوير ليعود الخادم إلى استخدام `DATABASE_URL` الاحتياطي. وبما أن النقل لا يحذف من MySQL، تظل قاعدة المصدر مرجعاً آمناً إلى أن يعتمد تشغيل الإنتاج رسمياً.
